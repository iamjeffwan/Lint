## 1. 产品背景与问题

### 1.1 现实痛点

- 越来越多个人开发者与小团队用 **AI（Cursor / Copilot 等）写 UI**。
- 模型为了「好看 / 还原设计图」，容易写出：
  - 任意值：`p-[13px]`、`w-[333px]`
  - 硬编码颜色：`bg-[#ff6600]`
  - 不在主题阶梯内的间距、圆角、字号
- 结果是：**代码与设计体系脱节**，后期难维护，品牌与组件库不一致。

### 1.2 要解决的问题

| 角色 | 痛点 | 产品要提供的 |
|------|------|----------------|
| 有成熟设计体系的团队 | Token 难稳定落到代码与 AI 约束 | JSON 导入 → 主题 + 可执行规则 |
| 无完整体系的个人/小公司 | 不知道从哪开始，又怕体系太薄 | 成熟主题底座 + 主色/次色等微调 |
| 用 AI 写前端的人 | 模型写歪、难发现、难修 | Lint 报错 + 修复引导 + 偏移可视化 |
| 产品/负责人 | 说不清「约束带来的价值」 | 页面上展示「控制了哪些偏移」 |

### 1.3 产品不是什么

- 不是又一个「主题换肤编辑器」
- 不是完整取代 Figma / Tokens Studio
- 不是自研一套与官方抢赛道的通用 Linter（短期）

### 1.4 产品是什么

**设计体系护栏（Design System Guardrails）**：

1. 把设计体系（或开源完整主题）变成 Tailwind / shadcn 可用的主题；
2. 生成以 `@shadcn/lint` 为核心的可执行约束；
3. 在开发中检查越界用法，并可视化「偏移被控制」的结果。

## 2. 核心概念：Tailwind 与设计体系

### 2.1 工具类（Utility Classes）

Tailwind 是 **utility-first**：在 HTML/JSX 中直接写预定义类名，构建时扫描源码，只生成用到的 CSS。

```
代码中的 class → 扫描匹配 → 映射为真实 CSS 规则
```

- **不是**任意起名都会映射；只有框架认识的类（内置、主题扩展、自定义 `@utility`、任意值语法等）才会生成 CSS。
- 类名须以**完整字符串**出现在源码中，动态拼接（如 `` `p-${n}` ``）可能导致扫描不到。

### 2.2 三层关系

| 层级 | 作用 | 典型手段 | 例子 |
|------|------|----------|------|
| **内置工具类** | 框架自带能力 | 默认主题 + 映射规则 | `p-4`、`bg-blue-500`、`flex` |
| **主题扩展** | 改/加设计令牌，自动生成对应工具类 | `@theme { --color-brand: ... }` | `bg-brand`、`p-18` |
| **自定义工具类** | 标准体系覆盖不到的能力 | `@utility` | `content-auto`、`stack-4` |

**建议**：优先扩展主题；仅在主题表达不了时再写 `@utility`。

### 2.3 用主题落实设计规范

若团队约定：

1. 只用 Tailwind 工具类；
2. **禁止任意值**（`[]` 语法）；
3. 不额外写游离的自定义 CSS（主题与规则文件除外）；

则样式被硬约束在 `@theme` 定义的令牌集合内。

**重要原则**：

- 主题是**设计可能性的全集**，不是「当前代码用到的子集」。
- **不要**因为「暂时没用到」就从主题里删除 token；否则后续页面与模型可选空间变小，更容易被迫写任意值。
- 「多余」应相对设计体系判断，而不是相对当前仓库使用率。

### 2.4 可覆盖的主题命名空间（节选）

| 命名空间 | 工具类示例 | 说明 |
|----------|------------|------|
| `--color-*` | `bg-primary`、`text-muted` | 颜色 |
| `--spacing-*` | `p-4`、`gap-8` | 间距 / 部分尺寸 |
| `--font-*` | `font-sans` | 字体族 |
| `--text-*` | `text-sm`、`text-xl` | 字号 |
| `--radius-*` | `rounded-lg` | 圆角 |
| `--shadow-*` | `shadow-md` | 阴影 |
| `--breakpoint-*` | `md:`、`lg:` | 响应式断点 |
| … | … | 字重、行高、模糊等 |

覆盖示例：

```css
@import "tailwindcss";

@theme {
  --font-sans: "Inter", "PingFang SC", system-ui, sans-serif;
  --spacing-4: 1rem;
  --color-brand: #1da1f2;
  --breakpoint-3xl: 120rem;
}
```

## 3. 从设计到主题：落地路径

### 3.1 有成熟设计体系时

```
Figma Variables / Tokens Studio
        ↓ 导出 JSON（建议接近 W3C Design Tokens）
转换（插件 / Style Dictionary / 自研脚本）
        ↓
Tailwind v4 @theme
        +
shadcn 语义 CSS 变量（:root / .dark）
```

**Figma 侧可选工具（示例）**：Tokens Studio、Tokens Exporter to CSS、Variables Xporter、各类 Tailwind v4 `@theme` 导出插件等。

命名建议（便于转换）：

- 颜色：`color/brand/500`、`color/text/primary`
- 间距：`spacing/4`
- 圆角：`radius/md`

### 3.2 无完整体系时（个人 / 小公司）

**不必强依赖 Figma。** 推荐路径：

1. 选用**完整开源主题底座**（见下）；
2. 只微调品牌相关色（主色、次色等）；
3. 保持间距、中性色、字号、圆角等阶梯完整；
4. 再进入约束与 Lint。

#### 适合小团队的开源参考

| 方案 | 类型 | 说明 |
|------|------|------|
| **shadcn/ui 官方主题** | 代码 | 语义变量完整，改 primary 等即可品牌化 |
| **Preline UI** | 代码 + Figma | 免费核心丰富，适合预算有限团队 |
| **Flowbite** | 代码 + Figma | 设计与组件对应清晰 |
| **Myna UI** | Figma + 代码 | 对齐 shadcn / Radix / Tailwind |
| **Plus UI 等** | Figma | 免费设计系统向 token |

#### 品牌色微调（标准做法）

保留完整阶梯，仅改语义色，例如：

- `--primary` / `--primary-foreground`
- `--secondary` / `--secondary-foreground`
- 按需：`--accent`、`--destructive`、`--muted` 等

产品内可提供「选主色 / 次色 → 预览组件 → 写入主题」的能力（对标 shadcn Themes、TweakCN 等体验）。

### 3.3 与 shadcn 对齐

shadcn 组件依赖语义 CSS 变量。同一套 Token 建议输出两路：

1. Tailwind `@theme`（工具类）
2. `:root` / `.dark` 下的 shadcn 变量（组件）

避免「工具类一套色、组件另一套色」。

### 3.4 兼容性检查的正确语义

| 检查类型 | 目的 | 是否删主题 |
|----------|------|------------|
| 代码超出主题（任意值、未定义 token） | 修代码或**扩展**主题 | 否 |
| 主题缺少关键语义 token | 补全主题 | 否 |
| 主题有但代码暂未使用 | 可选统计 | **默认不删** |

## 4. 产品闭环与流程

### 4.1 主流程

```
┌─────────────────────────────────────────────────────────┐
│  1. 主题接入                                              │
│     · 有体系：导入设计 Token JSON                         │
│     · 无体系：选择成熟主题 + 微调（主色/次色/少量阶梯）      │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  2. 生成产物                                              │
│     · @theme CSS                                          │
│     · shadcn 变量                                         │
│     · @shadcn/lint 规则配置（及 AI 项目规则片段）            │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  3. 约束下的开发                                          │
│     · 人 / 模型只使用主题内工具类与约定组件用法              │
│     · 项目规则明确禁止任意值与硬编码色                      │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  4. 检查与修复                                            │
│     · @shadcn/lint（ESLint / Oxlint）                     │
│     · 报错信息面向 agent：说明问题 + 建议合法替代           │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌─────────────────────────────────────────────────────────┐
│  5. 价值可视化                                            │
│     · 偏移项列表、类别统计、已控制 / 仍风险                  │
│     · 用于产品页展示「护栏实际拦住了什么」                   │
└─────────────────────────────────────────────────────────┘
```

### 4.2 两类用户路径

**路径 A — 有成熟体系**

1. 导出 / 准备 Token JSON  
2. 导入本产品 → 映射为 `@theme` + shadcn 变量  
3. 生成 lint 与 AI 规则  
4. 接入仓库 → 开发 → 检查 → 看报告  

**路径 B — 无完整体系**

1. 选择内置/推荐成熟主题  
2. 微调主色、次色等  
3. （可选）少量扩展间距档位等，**不删减完整阶梯**  
4. 同上生成约束 → 开发 → 检查 → 报告  

### 4.3 完整主题建议覆盖（宁多勿少）

- **颜色**：中性色阶梯、品牌色阶梯、语义色（success/warning/error）、前景/背景/边框等  
- **间距**：完整 scale（如 0–32 或设计约定的全阶梯）  
- **字体**：sans / 展示用字体等  
- **字号、圆角、阴影、断点**  

保证模型在约束内仍有足够组合空间。

## 5. 检查底座：@shadcn/lint

### 5.1 项目概况

| 项 | 内容 |
|----|------|
| 包名 | `@shadcn/lint` |
| 仓库 | https://github.com/shadcn-ui/lint |
| 定位 | Agent-first linter for Tailwind design systems |
| 许可 | MIT |
| 要求 | Tailwind v4；**不强制**使用 shadcn/ui 组件 |
| 宿主 | ESLint ≥ 9.30 或 Oxlint ≥ 1.80；Node ≥ 20.19 |
| 框架 | React / Vue / Svelte |

### 5.2 与本产品的契合点

- 专为 **AI agent 可验证、可自修复** 设计；
- 读取项目主题（`@theme`）、组件与 variants；
- 规则直接覆盖：任意值、原始颜色、未知 class、组件乱改样式等。

**核心规则（节选）**

| 规则 | 作用 |
|------|------|
| `no-arbitrary-values` | 禁止 `p-[13px]` 等 |
| `no-raw-colors` | 强制使用主题色 |
| `no-unknown-classes` | 类须能被当前 Tailwind 生成 |
| `no-restyle` | 限制对设计系统组件的样式覆盖（可配 contracts） |
| `no-inline-styles` | 限制内联样式 |
| `require-static-classes` | 类名需静态可读，便于扫描 |

### 5.3 在本产品中的角色

```
本产品：主题生命周期 + 规则包生成 + 报告可视化
              ↓ 生成配置
@shadcn/lint：执行检查 + agent 友好诊断
```

- **底座**：检查引擎用官方实现，避免自研同等复杂度的引擎。  
- **护城河**：主题导入/选主题/微调、一键规则包、偏移产品化展示。

### 5.4 宣传关系（借力不附庸）

- 可写：「基于 `@shadcn/lint` 的设计体系护栏」以建立信任。  
- 主叙事仍是：**主题 → 可执行约束 → 偏移可见**，而非「官方附属 UI」。  
- 避免产品定位完全绑定单一上游叙事。

### 5.5 若官方不足时

| 能力 | 策略 |
|------|------|
| 任意值 / 主题色 / 未知 class 等 | 优先依赖 `@shadcn/lint` |
| 主题接入与可视化报告 | 必须自建 |
| Programmatic API / Biome 等 | 跟进上游 issue；必要时自研**薄**扫描与报告适配层 |
| 上游停更或严重不满足 | 再评估自研规则引擎（非 MVP 优先） |

### 5.6 跟进与维护

1. Watch Releases / CHANGELOG；  
2. 锁定支持的版本范围，升级前用样例项目回归「生成配置 → lint → 报告」；  
3. 内部使用自有「规则描述 / 报告模型」，再映射到 lint 配置，降低耦合；  
4. 适度参与社区（如更利报告的 API 需求）。

## 6. 产品形态与模块

### 6.1 形态选择

| 形态 | 优先级 | 说明 |
|------|--------|------|
| **Web 应用** | P0 | 易演示、易引流、承载主题配置与报告可视化 |
| **CLI** | P1 | `check`、进 CI、开发者口碑 |
| 编辑器扩展（Cursor/VS Code） | P2 | 写代码时即时提示 |
| 桌面应用 | 暂缓 | 安装与分发成本高 |

**原则**：Web 讲清价值与获客；CLI/扩展嵌入工作流。

### 6.2 功能模块

#### A. 主题接入

- 导入设计 Token JSON（成熟体系）  
- 选择内置/推荐开源主题（无完整体系）  
- 微调：主色、次色、必要语义色；可选有限阶梯扩展  
- 导出：`@theme`、shadcn 变量文件  

#### B. 约束生成

- `@shadcn/lint` 规则与 contracts 默认集  
- 项目级 AI 规则片段（如 AGENTS.md / Cursor rules）  
- 说明：禁止任意值、仅用主题 token、组件用法约定  

#### C. 检查与修复

- 对接 ESLint/Oxlint 运行 `@shadcn/lint`  
- 展示单条诊断与建议  
- （可选）引导「改 class」或「扩展主题」两条路径  

#### D. 价值可视化（产品差异化关键）

- 偏移数量与分类（任意值、原始色、未知类、非法 restyle…）  
- 已修复 / 仍存在  
- 用于官网与用户后台证明「护栏有效」  

### 6.3 对外产品定义（可直接使用）

> 一个面向 AI 前端开发的设计体系约束平台：  
> 接入或选择主题 → 生成可执行规则 → 检查并可视化代码对体系的偏移。

## 7. 市场、竞品与差异化

### 7.1 生存空间

- **有空间**：AI 写 UI 普及 + 设计体系落地难 + 工具链碎片化（主题工具、Token 流水线、Lint 各做一段）。  
- **切口**：不是「再做一个设计系统平台」，而是 **AI 开发时的设计体系护栏 + 偏移可视化**。  
- **谨慎**：纯主题编辑器已有竞品；纯禁任意值 Lint 过薄，难单独成为产品。

### 7.2 竞品对照

| 类型 | 代表 | 强项 | 本产品差异 |
|------|------|------|------------|
| 主题定制 | shadcn Themes、TweakCN | 改色与导出 | 加上约束、Lint、偏移展示 |
| Token 流水线 | Tokens Studio、Style Dictionary | 设计→多平台同步 | 更偏开发时约束与 AI |
| 静态规范 | 通用 ESLint/Stylelint | 检查 | 与主题/组件/agent 修复话术深度结合 |
| AI 编码 | Cursor、Copilot | 生成代码 | 不管体系边界；本产品补边界 |

### 7.3 差异化一句话

> 不是帮你「做出一套主题」，而是帮你「把主题变成 AI 和代码都跑不出去的边界，并把偏移可视化」。

三点卖点：

1. 主题完整且可微调  
2. 规则可执行（`@shadcn/lint` + AI 规则）  
3. 偏移可看见（报告页）

## 8. 宣传与起号策略

### 8.1 对外定位句

> 给 AI 写前端加上设计体系护栏：主题进得来，代码跑不出去，偏移看得见。

### 8.2 内容方向

1. **前后对比**：无约束时满屏任意值 vs 有护栏后落入主题阶梯（配报告截图）。  
2. **小团队场景**：只有品牌色、没有完整 Figma 体系时，如何 3 步上约束。  
3. **与 Cursor 结合**：规则进项目，模型只在体系内写，lint 闭环修复。  
4. **开源引流**：可开源「默认规则包示例」或文档，完整可视化与主题管理作产品层。

### 8.3 渠道建议

- 中文：即刻、小红书、V2EX、技术博客  
- 英文：X、Reddit（r/webdev、r/tailwindcss）、独立开发者社区  
- 叙事可双语：中文偏「小团队/个人」，英文偏 *design system guardrails for AI coding*

## 9. MVP 与实施优先级

### 9.1 MVP（先能演示、能讲故事）

1. 选主题 **或** 导入简化版 JSON  
2. 微调 primary / secondary  
3. 导出 `@theme` + 基础 `@shadcn/lint` 配置（至少含 `no-arbitrary-values`、`no-raw-colors` 等）  
4. 粘贴/上传代码片段或连接示例仓 → 生成**偏移报告页**  

### 9.2 第二阶段

- 更完整的 Token 映射与 shadcn 变量同步  
- CLI：`npx <product> check`  
- 规则包可配置（contracts、allow 列表）  
- AI 规则一键导出  

### 9.3 第三阶段

- 编辑器扩展  
- CI 集成模板  
- 历史趋势、团队策略模板  
- 按需加深与上游 API 的集成  

### 9.4 明确不做（早期）

- 从零自研完整 agent-level design-system linter  
- 重型桌面端  
- 承诺替代整套企业设计系统平台

## 10. 风险、依赖与跟进策略

### 10.1 依赖 `@shadcn/lint`

| 风险 | 缓解 |
|------|------|
| 配置/API 变更 | 适配层 + 版本锁定 + 回归样例 |
| 官方扩展到主题可视化 | 强化「导入/选主题/运营报告」差异 |
| 仅 ESLint/Oxlint | 文档写清环境；关注 programmatic API 进展 |
| 停更或质量下降 | 报告层可接备用扫描；引擎替换有成本但模块化可降痛 |

### 10.2 产品风险

- 与「只做主题」的工具同质化 → 坚持闭环与可视化。  
- 用户期望自动删「未使用 token」→ 产品文案与默认策略坚持**保留完整主题**。  
- 检查过严导致落地困难 → 支持 warn 起步、分目录 overrides（与官方 adoption 指南一致）。

### 10.3 成功标准（示例）

- 用户能在 30 分钟内完成：选主题/导入 → 生成规则 → 看到首份偏移报告。  
- Agent 在启用规则后，任意值/原始色类问题显著下降（可用前后对比内容验证）。  
- 报告页能被用于对外演示「护栏价值」。

### 11.1 术语表

### 11.3 AI 项目规则示例（可放入 AGENTS.md）

```text
设计体系约束：
1. 只能使用主题（@theme / 项目 CSS 变量）中已定义的 token 对应工具类。
2. 禁止任意值语法（p-[..]、bg-[#..]、w-[..] 等），除非规则明确允许的例外。
3. 颜色、间距、圆角、字体必须来自设计体系；不要写死魔法数字与色值。
4. 修改主题只能改主题文件，不要在业务组件里用任意值绕过。
5. 使用设计系统组件时，遵守 variants / contracts，不要随意用 className 覆盖组件自身样式。
6. 改完 UI 后运行项目 lint（含 @shadcn/lint），根据报错修复至通过。
```
