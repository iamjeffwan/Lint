# 工单五：项目环境检测工具核对

- 核对日期：2026-09-28。
- 状态：供方案讨论，尚未实现或确定全部取舍。
- 方法：读取官方文档及官方源码。样式框架官网本次返回访问限制，改为核对同一项目的官方文档源码；没有以第三方文章替代。
- 边界：只研究基础环境，不自行解析组件库配置，不增加组件约束。

## 1. 项目根目录与包管理器

**官方事实：**`npm`（包管理器）通过包描述文件的 `workspaces`（工作区声明）定义子包目录或匹配模式。`pnpm`（另一种包管理器）的工作区文件也保存普通设置；当前文档原文是：“If the packages field is omitted, only the root package is included in the workspace.”（如果省略包列表字段，工作区仅包含根包。）因此不能把这个文件存在直接解释为已发现多个应用。

**本项目建议：**先从目标目录向上定位最近的包描述文件，再检查祖先是否把目标声明为工作区成员。目录名字或随便出现第二个包描述文件都不是充分证据。识别到真实工作区成员后按已确认政策停止；只有设置、没有子包声明的单包情形应单独说明，避免误报。包管理器声明和锁定文件冲突时输出“存在冲突”，不要随意选择一个。

来源：[包描述文件与工作区](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#workspaces)、[工作区配置](https://pnpm.io/pnpm-workspace_yaml)、[包管理器声明](https://nodejs.org/api/corepack.html)。访问日期：2026-09-28。

## 2. 已声明版本与实际安装版本

**官方事实：**`createRequire`（创建指定文件位置的模块解析上下文）允许以绝对路径构造解析器。`semver`（语义化版本比较工具）分别处理具体版本和版本范围。包的 `exports`（公开导出声明）还可能阻止直接读取其包描述文件。

**本项目建议：**以目标项目的包描述文件为基准解析依赖，不能从我们的命令行工具目录解析。分别记录“声明范围”“实际安装版本”“解析状态”；缺少安装时不能把声明范围当作已安装版本。只读取目标包元数据，不为查版本执行包入口。元数据路径未公开时，需要有边界的定位逻辑，核对包名并处理解析失败。包管理器锁定文件用于识别环境，不在第一版各写一套完整版本求解器。

备选：较新的 `findPackageJSON`（查询包描述文件位置）能帮助定位，但官方仍标记为活跃开发接口，需结合我们的运行时最低版本选择。无法可靠解析的特殊安装方式应显示未确认，不能借用工具自己的依赖冒充目标版本。

来源：[模块接口](https://nodejs.org/api/module.html#modulecreaterequirefilename)、[包导出限制](https://nodejs.org/api/packages.html#subpath-exports)、[版本工具官方说明](https://github.com/npm/node-semver)。访问日期：2026-09-28。

## 3. 文件发现

**官方事实：**`fast-glob`（文件模式查找工具）提供扫描目录、排除模式、深度、文件类型和符号链接跟随选项。它负责找到文件，不判断这些文件是否参与应用运行。

**本项目建议：**使用这个工具发现有限范围内的候选文件；由我们统一排除依赖、构建产物、版本管理目录及环境变量文件，设置数量与大小上限。默认不跟随目录符号链接，扫描不完整时显式记录，避免误报“没有配置”。

来源：[工具官方说明](https://github.com/mrmlnc/fast-glob#options)。访问日期：2026-09-28。

## 4. 样式文件解析与主题识别

**官方事实：**`PostCSS`（样式语法解析工具）的解析入口返回语法树。`Tailwind CSS v4`（第四版原子样式框架）导入框架时已经包含默认主题；本地没有 `@theme`（自定义主题声明）也可以正常使用。`@config`（旧式配置加载指令）是第四版官方兼容能力，出现旧式配置文件不能单独证明项目仍是第三版。

**本项目建议：**只调用样式解析器，不加载用户样式插件。识别框架导入、主题声明、本地样式导入及兼容配置引用，区分“框架入口已找到”和“存在自定义主题”。由我们处理文件之间的导入关系及相对路径输出。

局限：语法树只能证明文件写了什么，不能证明构建成功、主题最终生效或不存在层叠覆盖。

来源：[解析器官方源码](https://github.com/postcss/postcss/blob/main/lib/parse.js)、[默认主题文档源码](https://github.com/tailwindlabs/tailwindcss.com/blob/main/src/docs/theme.mdx)、[兼容指令文档源码](https://github.com/tailwindlabs/tailwindcss.com/blob/main/src/docs/functions-and-directives.mdx)。访问日期：2026-09-28。

## 5. 构建接入和应用入口

**官方事实：**第四版官方安装分别提供 `@tailwindcss/vite`（构建工具插件）与 `@tailwindcss/postcss`（样式处理插件），都还需要在样式文件导入框架。安装了插件依赖不等于已经在构建配置启用。

**本项目建议：**分开记录“依赖安装”“构建接入证据”“应用入口到样式文件的静态引用链”。先支持明确的常见入口；动态配置、自定义别名、复杂导入不能解析时给未确认状态，不执行整个构建来猜测。需要决定第一版是否只保证常见构建工具项目，其他框架返回人工确认。

来源：[构建工具安装文档源码](https://github.com/tailwindlabs/tailwindcss.com/blob/main/src/app/%28docs%29/docs/installation/%28tabs%29/using-vite/page.tsx)、[样式处理安装文档源码](https://github.com/tailwindlabs/tailwindcss.com/blob/main/src/app/%28docs%29/docs/installation/%28tabs%29/using-postcss/page.tsx)。访问日期：2026-09-28。

## 6. 源码导入关系解析

**官方事实：**`TypeScript Compiler API`（类型脚本编译器接口）可创建和遍历源码语法树；`typescript-estree`（转换为通用语法树的解析器）在编译器之上转换语法树，支持不进行类型分析的解析。

**本项目建议：**两者选一个，不同时安装两套。只为追踪导入，直接用前者即可；若以后大量复用通用语法树生态，可选后者。成熟工具负责正确解析语法，我们负责入口发现、文件解析、别名范围、导入链和循环去重。

补充工具：`get-tsconfig`（类型脚本配置读取工具）支持注释、尾逗号和配置继承；其路径匹配方法只返回候选路径，不做实际解析。官方常见问题也说明：已经依赖编译器时可以直接使用编译器接口。因此本项目若选择官方编译器，建议同时复用其配置读取能力；是否另加这个小工具是易用性取舍，不是必要条件。类型脚本别名存在也不能证明构建工具配置了相同别名。

局限：解析到导入语句不代表目标可解析；静态引用链也不等于浏览器运行时验证。

来源：[官方编译器使用说明](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)、[解析器官方接口](https://typescript-eslint.io/packages/typescript-estree/)、[配置工具官方说明](https://github.com/privatenumber/get-tsconfig)。访问日期：2026-09-28。

## 7. 检查器配置验证

**官方事实：**`ESLint`（代码检查器）提供 `loadESLint`（加载检查器实现）、`calculateConfigForFile`（计算指定文件的有效配置）和 `isPathIgnored`（查询文件是否被忽略）。配置可能是可执行脚本，类型脚本配置还可能要求目标项目具备额外加载能力。

**本项目建议：**使用目标项目安装的版本，在独立子进程内把工作目录设置为目标目录，选择真实业务源码样本并查询是否忽略、能否计算有效配置。不强行注入我们的配置，也不直接执行用户的检查脚本。记录探测过的文件范围；一个样本成功不能表述为所有文件的规则都可运行。

取舍：只看配置文件存在，快但不能确认可加载；调用官方接口更可靠，但会执行配置及其导入。子进程便于隔离进程状态和设置超时，**不是安全沙箱**。因此“只做静态检测”不能同时描述这个步骤。旧版本缺少所需接口时应明确支持范围，不悄悄换成我们的版本。

来源：[官方程序接口](https://eslint.org/docs/latest/integrate/nodejs-api)、[配置文件说明](https://eslint.org/docs/latest/use/configure/configuration-files)。访问日期：2026-09-28。

## 8. 各步骤如何交接

以下是产品建议，不是上述工具自动提供的能力：

1. 目录定位输出扫描根目录与结构结论；发现禁止的工作区后停止后续检测。
2. 文件发现与依赖解析输出本地共享上下文，供样式检查和检查器配置验证复用。
3. 每项检测输出事实、状态、依据、问题及建议；不在各检测器里抢先计算最终支持结论。
4. 工单六补充官方组件库查询结果；不为复用查询而自建组件库配置解析器。
5. 工单七合并事实并判断能否继续；工单四执行结果校验、快照保存和上传。

工具解析出的配置对象、源码和绝对路径只在本地使用。上传前按共享协议重新构造允许字段；不能直接上传官方查询的原始输出或子进程错误全文。

成熟工具解决解析和执行机制；项目根目录策略、证据强度、支持范围、失败交接与可读提示需要我们实现。建议先确认“入口支持范围”和“动态配置验证范围”，再固定工单五验收样例。
