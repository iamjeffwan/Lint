## 先理解我们准备做什么

命令行工具是一个通过终端接收参数、执行工作并输出结果的程序。我们准备使用 `Node.js`（在浏览器之外运行脚本的环境）运行它，使用 `TypeScript`（带类型检查的脚本语言）编写它。

用户电脑上的终端负责启动程序；我们的程序负责读取参数、组织本地检测和上传结果；服务端负责接收结果。终端本身不负责检测，服务端也不会因为收到项目路径就能读取用户电脑里的文件。

```mermaid
flowchart LR
    A[用户在终端执行命令] --> B[启动我们的本地程序]
    B --> C[读取参数与当前目录]
    C --> D[调用检测逻辑]
    D --> E[生成结构化结果]
    E --> F[发送到服务端]
    F --> G[终端显示成功或失败]
```

这是一条本项目的学习路线，不代表以下某一本官方手册会完整教会这条流程。

## 1. 程序怎样知道用户输入了什么、在哪个目录执行

资料：[进程官方文档](https://nodejs.org/api/process.html)。这是 `Node.js`（脚本运行环境）的参考手册，不是从零搭建工具的课程。

先读三个小节：

- [`process.argv`（启动参数数组）](https://nodejs.org/api/process.html#processargv)：前两项通常是运行程序的可执行文件路径和脚本路径，后面才是传入脚本的参数。
- [`process.cwd()`（当前工作目录）](https://nodejs.org/api/process.html#processcwd)：得到用户启动程序时所在的目录。它不等于我们工具源码所在的目录。
- [`process.exitCode`（退出状态码）](https://nodejs.org/api/process.html#processexitcode)：向调用者报告程序是否成功。直接强制退出可能截断尚未完成的输出，官方退出方法章节对此有说明。

读完应该能回答：为什么同一个工具，在两个不同的项目目录里执行，会检测两个不同的项目？因为它把当前工作目录作为默认检测目标，而不是扫描工具自己的安装目录。

优点：概念直接对应工单四，了解三项就能建立基本认识。局限：整页很长，不适合从头到尾阅读。访问日期：2026-09-28。

## 2. 怎样把原始参数变成好用的命令

资料：[`Commander.js`（命令行参数解析工具）的官方快速开始](https://github.com/tj/commander.js#quick-start)。这是最建议先跟读的示例式入门材料。

依次看快速开始、选项、命令、帮助信息四部分。官方会示范怎样声明子命令和选项，并自动处理未知选项、使用错误和帮助输出。

对应本项目：工具需要读取检测任务编号、令牌、服务地址和目标目录。它们的解析、缺少参数时的提示、帮助说明，可以交给该工具；本地检测和网络上传仍要由我们的程序实现。

优点：示例短，能直接理解“一个命令如何写出来”。局限：它只解决命令入口，不负责检测业务、网络恢复或打包发布。访问日期：2026-09-28。

## 3. 为什么用户能用一个包名运行我们的程序

资料：`npm`（脚本包管理器）的三段官方说明：

- [`bin`（可执行命令映射）](https://docs.npmjs.com/cli/v11/configuring-npm/package-json/#bin)：在包描述文件里把命令名指向入口脚本。官方也说明了微软操作系统上的命令启动文件，并要求入口脚本声明使用何种运行程序。
- [`npm link`（本地开发链接）](https://docs.npmjs.com/cli/v11/commands/npm-link/)：用于在本地测试尚未发布的包。它会建立链接，包括全局位置的链接，并非只影响当前文件夹。
- [`npx`（执行包中命令的工具）](https://docs.npmjs.com/cli/v11/commands/npx/)：运行本地已有包的命令，或者获取指定包再执行；缺少的包会安装到包管理器缓存目录。

对应本项目：我们写出的脚本先要有可执行入口，再打包成可分发的工具。开发时可以直接运行构建后的脚本，也可以使用本地链接，不需要为了第一次联调就公开发布。以后面向用户发布后，网页才能提供可正常获取的包执行命令。

优点：能解释“编写脚本”和“提供一个可安装命令”之间差了什么。局限：这些都是机制参考，需要和上面的命令示例配合阅读。访问日期：2026-09-28。

## 4. 编译和发布为什么是两件事

资料：[`TypeScript`（类型化脚本语言）官方五分钟入门](https://www.typescriptlang.org/docs/handbook/typescript-tooling-in-5-minutes.html)。这是入门文章，重点读编译第一个程序，不需要在此时深入类型系统。

官方通过一个简单文件说明：编译器把源文件转换成 `JavaScript`（运行时执行的脚本）。对于我们计划采用的分发方式，命令入口应指向准备给用户运行的产物，而不是默认要求用户安装我们的开发工具。

编译解决“源代码如何成为运行产物”；发布解决“用户从哪里取得这个工具”。是否需要发布、发布哪些文件，还要看上一节的包管理器配置。不能把类型检查通过当成包已经可供用户下载。

优点：示例清楚，适合补齐编译概念。局限：不是命令行打包教程，其浏览器示例也不等于本项目的运行方式。访问日期：2026-09-28。

## 5. 本地工具怎样向服务器上传结果

资料：[`fetch`（网络请求函数）的官方说明](https://nodejs.org/api/globals.html#fetch)。这是接口参考，页面包含请求和响应示例。

对应本项目：命令行程序向服务端发起请求，携带任务令牌和结构化检测结果，然后检查响应是否成功。这个函数可直接由本地运行环境提供，不需要把上传操作交回浏览器。

学习时把“得到一个响应”和“上传成功”分开理解：我们仍要判断响应状态、读取业务错误，并处理超时和网络中断。网络请求工具不会自动实现一次性令牌的业务规则。

优点：与网页开发的网络请求方式相近，可以减少额外依赖。局限：官方参考不会替我们设计重试、任务过期和重复提交流程；这些仍以项目协议为准。访问日期：2026-09-28。

## 6. 我们的程序怎样调用另一个命令行工具

资料：[`Execa`（子进程执行工具）的官方说明与示例](https://github.com/sindresorhus/execa)。先看最简单的执行示例、本地可执行程序、详细错误三个部分。

它基于运行环境的子进程能力，提供执行命令、取得标准输出和捕获失败信息等功能。对应本项目：后续调用 `shadcn CLI`（官方组件工具）时，需要启动另一个本地进程，再读取它返回的数据。

标准输出用于传递正常结果，标准错误通常用于诊断信息；二者不宜混在一起当作结构化结果解析。工单四先理解这种机制，具体官方查询接入属于工单六。

优点：对本地可执行程序和微软操作系统做了便利处理，适合我们的跨平台目标。局限：工具能帮助启动进程，但不会自动保证被调用程序的输出格式长期稳定。不要把所有高级管道示例都作为当前学习目标。访问日期：2026-09-28。

## 建议阅读顺序

先读第二项的快速开始，再用第一项理解参数、目录和退出状态；随后阅读第三项，弄清入口与分发。第四项按已有基础补读，第五项用于理解上传，第六项在准备接入官方查询前阅读。

工单四开始前，能够说清下面三件事就够了：

1. 用户输入的命令怎样启动我们的程序，参数怎样交给程序。
2. 工具自己的安装目录，与准备检测的项目目录为什么不同。
3. 检测结果怎样通过网络发送给服务端，以及失败为什么要返回明确状态。

这些资料用于帮助理解，不表示需要先完成一套大型命令行框架课程，也不改变已经确认的工单实施顺序。
